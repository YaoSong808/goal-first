# Goal First · 目标优先

**项目初期先理解用户意图，再判断方案，必要时介入。**

[English](README.md) | [技能正文](SKILL.md) | [行为检查场景](references/behavior-cases.md)

Goal First 是一个轻量的 Codex 技能。它要求 AI 在项目初期先弄清用户想解决什么问题、谁会使用成果、怎样才算完成，以及必须满足什么约束。在建立共同理解之后，再判断用户提出的方案是否合适，必要时提出更直接的实现路径。

核心顺序是：**理解意图 → 判断方案 → 必要时介入 → 推进执行**。

## 为什么做这个技能

用户在项目初期经常用一个方案来表达需求：“做一个网站”“开发一个 App”“搭一套自动化流程”。这些表达说明了用户目前想到的做法，但未必已经说清最终目的、使用场景和成功标准。

AI 如果直接选技术、拆功能、写代码，可能很高效地把一个没有对齐真实意图的方案做完。等到用户补充关键背景时，才发现前面的开发和流程并不必要。反过来，AI 没理解用户就抢先推荐“更简单的办法”，也可能否定用户真正重视的东西。

因此，这个技能首先解决的是**项目初期的意图理解与对齐**。AI 应先利用已有上下文理解目标；对会影响方向的不确定信息，简短复述自己的理解并向用户核实。不能把自己的推测当成用户已经确认的意图。

理解清楚之后，才有依据判断是否需要介入：原方案符合目标，就继续执行；存在明显绕路，才说明原因、替代路径与取舍。即使方案看起来并不复杂，也应在项目起步时理解意图，而不是等发现浪费之后才补问需求。

已有上下文足够时，不需要再走一轮确认；明确的小修复也不必重新讨论整个项目。关键是尽早对齐方向，而不是增加一套审批流程。

## 它会改变什么

| 遇到的情况 | 期望行为 |
| --- | --- |
| 项目刚开始，只有方案名称，目标和使用场景还不清楚 | 先理解意图，澄清会影响方向的信息，再选方案。 |
| 用户纠正了 AI 对需求的理解 | 更新理解和建议，不坚持自己的“真实需求”猜测。 |
| 把“部署”直接等同于“必须重写技术栈” | 在投入重写前，把两件事分开判断。 |
| 为偶尔发生的任务建设一整套平台 | 先考虑已有工具或小脚本，说明主要取舍。 |
| 项目中途出现改变前提的新信息 | 重新判断路线，保留已有工作的价值。 |
| 只是一个明确的小修复 | 直接做，不输出一套必要性评审。 |
| 学习、所有权或团队标准就是目标的一部分 | 尊重这些约束，不拿“更简单”替换用户真正想要的结果。 |
| 用户已经了解取舍并做出选择 | 继续推进，不反复劝退。 |

这里的“省事”指的是**总负担更小**：首次设置、日常操作、长期维护、费用、可靠性、数据一致性和迁移成本都要考虑。代码更少、组件更少或者订阅更便宜，不一定代表整体更合适。

## 一次好的介入是什么样

例如，用户只说“做一个网站，让我在外面也能处理业务”，AI 应先了解实际用途和已有条件，而不是立即选技术或劝用户放弃网站：

> 我理解你想解决的是在外面处理业务的问题。这个入口主要给你自己使用，还是也给员工、客户使用？现在是否已有能处理这些业务的程序？

当用户说明只有一两人使用、已有可运行的 ERP，且家里电脑可以保持开机后，才有依据提出：

> 既然目标是远程使用已有 ERP，重写前后端并不是前提。可以先验证私有访问是否满足需求；它依赖家里的电脑和网络持续可用，如果无法保证，再考虑云端。

出差只是一个例子。同样的判断适用于新产品、数据分析、学习项目、采购和流程设计。需要核实的条件应当核实，不能把“可能适合”说成“已经验证可用”。

## 它不会做什么

- 不会以“更简单”为由，删掉必要功能或擅自改变交付物。
- 不会在意图尚未弄清时，就断言“你真正需要的是……”并替用户改方向。
- 不会把每个请求变成长问卷、比较表、打分表或审批流程。
- 不会因为用户不熟悉技术，就默认用户的需求不合理。
- 不会把不上云、不写程序、不做大项目当成固定结论。
- 不会反复挑战已经充分说明的约束和知情选择。
- 不会因为发现替代路线，就擅自删代码、取消服务、迁移数据或花钱。

技能自身也遵守同一条原则：检查的成本，应当低于它有希望节省的成本。没有具体收益，就直接做事。

## 安装

这个仓库本身就是技能目录，根目录下有 `SKILL.md`。它不需要服务器、不需要安装应用依赖、不需要单独的 API Key，也没有后台服务；需要的是支持技能的兼容代理环境。

### 通过 Codex 的技能安装器

在有 `$skill-installer` 的环境中直接说：

```text
使用 $skill-installer 安装 https://github.com/YaoSong808/goal-first。
技能位于仓库根目录，请以 goal-first 为名称安装。
```

让安装器使用当前环境配置的技能目录。如果已经装过，就更新已有副本，不要重复安装。

安装器下载失败时，请使用下方的完整手动克隆。部分安装器版本在用 Git 备用方式安装仓库根目录技能时会漏掉子目录。完整安装应包含 `agents/openai.yaml` 和 `references/behavior-cases.md`，不应只有 `SKILL.md`。

### 手动安装

macOS 或 Linux 上首次安装时，可使用[官方技能文档](https://learn.chatgpt.com/docs/build-skills)列出的用户级目录：

```bash
mkdir -p ~/.agents/skills
git clone https://github.com/YaoSong808/goal-first.git ~/.agents/skills/goal-first
```

部分安装环境使用 `$CODEX_HOME/skills` 或 `~/.codex/skills` 管理技能。以当前环境能识别的目录为准，不要在两处各装一份。没有出现在技能列表时，可以新开会话或重启客户端。

手动克隆的副本可以在确认没有未处理的本地修改后，在该目录内运行 `git pull --ff-only` 更新。通过安装器安装的副本，则使用对应环境支持的更新方式。

## 如何使用

可以明确调用：

```text
使用 $goal-first。我想做一个客户管理工具，但具体需求还没理清。
请先结合已有信息理解我的目标，问清会影响方向的关键问题，
再判断适合采用什么方案，不要一开始就选技术栈。
```

也可以让它在已经确定的方向内检查：

```text
使用 $goal-first。我们已经因为家庭网络不稳定、员工需要
夜间访问，决定采用云端托管。请检查这个决定内部有哪些
多余步骤，然后继续部署工作，不要重新争论是否上云。
```

技能设置了 `allow_implicit_invocation: true`，允许宿主在请求匹配描述时自动选择它，但不保证每次都会触发。希望明确检查时，直接调用即可；各客户端的调用入口见[官方技能文档](https://learn.chatgpt.com/docs/build-skills)。

技能正文使用英文便于维护，明确要求跟随用户的语言交流；显示名称为中英双语，并提供中文起始提示。

日常工作不要求模型阅读 README 或全部验收场景。仓库没有额外执行脚本、定时任务或依赖包，详细介绍不会自动变成一套工作流程。

## 验证与改进

[14 个行为检查场景](references/behavior-cases.md)覆盖项目初期意图澄清、用户纠正理解、该提醒和不该打断的情况。它们是人工验收标准，不是成功率统计，也不表示已经完成独立模型评测。

评估修改时，先给模型技能和真实场景，不要提前给期望答案，再检查它实际说了什么、做了什么。除了检验能否指出多余步骤，也要检验它会不会打扰小任务、否定学习目标或反复挑战已确定的选择。

如果环境提供 Codex skill-creator 的 `quick_validate.py`，可用它检查本目录的结构和元数据；格式检查不能证明判断质量。修改后也应检查内部链接和界面配置是否一致。

欢迎根据具体失败案例改进。优先修正导致问题的那条规则，不要每遇到一个案例就新增通用流程。核心指令保持简短，更多例子放在参考文件；新框架、新服务或自动化流水线必须有实际收益再加。

这是对模型的行为指导，不是强制执行的程序。效果依赖模型、宿主和可用上下文。“你的方案已经合适，我们继续做”同样是正确结果。
